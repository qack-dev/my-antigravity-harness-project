# 0001. アーキテクチャ上の意思決定を記録する

## ステータス

採用

## コンテキスト

プロジェクトが進むにつれて、なぜその設計を選んだのかという背景は失われやすい。特にAIエージェントが後から作業を引き継ぐ場合、"何が決まっていて、なぜそう決まったのか"がコード上に残っていないと、既存の決定を無自覚に覆してしまうリスクがある。

本プロジェクトでは特に、(1) 対象プロジェクトの技術スタックを本リポジトリ側では決めない、(2) 生成器パターンを採用する、(3) ガードレールをHooksで実装する、(4) 未確認仕様は`[要確認]`で明示する、という一般的なソフトウェアプロジェクトとは異なる判断をしている。この経緯を残す必要がある。

## 決定

- このプロジェクトでは、後から覆すコストが高い設計判断を `docs/adr/NNNN-タイトル.md` という形式のADR(Architecture Decision Record)として記録する
- 本プロジェクト自体は実行可能なアプリケーションコードを持たない、静的なMarkdown/JSONテンプレート集として構成する。これは、本リポジトリの目的が「あらゆる技術スタックのプロジェクトに適用できる汎用ハーネス」を提供することであり、本リポジトリ自身が特定の言語・フレームワークを採用すると、その汎用性のメッセージと矛盾するためである
- 整合性チェック(`tests/validate-templates.mjs`)のみ、追加の依存パッケージを必要としないNode.js標準モジュールで実装する

## 影響

- 新しい重要な設計判断を行うAIエージェント・開発者は、実装前に対応するADRを作成する
- 既存のADRを覆す場合は、新しいADRを追加して古いADRのステータスを「廃止」に更新する(過去のADRは削除しない)
- 本リポジトリに実行可能なアプリケーションコード(例: 対話式CLIの自動化)を追加する提案が出た場合は、この決定を見直すADRを新規に起票すること
